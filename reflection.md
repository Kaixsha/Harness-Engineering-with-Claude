# Reflection Brief

## System 1: Stop-Reason-Driven Agentic Loop

### Loop Termination

The stop-reason-driven loop is implemented in:

`agentic-loop/src/agentic_loop.py`

The function responsible for controlling the loop is:

`run_agent()`

The loop examines the structured `stop_reason` value for every turn.

When `stop_reason` is `tool_use`, the requested tool is executed and the loop continues.

When `stop_reason` is `end_turn`, the function returns the final result and terminates processing.

This behavior is verified both by the automated test suite and by the end-to-end run artifact.

### Anti-Pattern Avoided

The implementation avoids determining completion by searching the model's natural-language response for words such as "done", "finished", or "complete".

Instead, termination depends on the structured `stop_reason` value.

This makes the loop deterministic and testable rather than depending on the wording generated by the model.

### End-to-End Evidence

The end-to-end claim demonstration is implemented in:

`agentic-loop/src/run_claims.py`

The run identifier is:

`agentic-loop-run-001`

The demonstration processes four sample claims:

- `CLM-2001`
- `CLM-2002`
- `CLM-2003`
- `CLM-2004`

Each processed claim terminates with one of two valid decisions:

- `route`
- `escalate`

The generated run artifact is:

`agentic-loop/artifacts/run-001.json`

The artifact records the turn-by-turn stop-reason trace.

The trace demonstrates that processing continues when the stop reason is `tool_use` and terminates when the stop reason becomes `end_turn`.

### Deterministic Enforcement

Deterministic claim-routing logic is implemented in:

`agentic-loop/src/claims.py`

The function:

`route_claim()`

checks required claim information, validates the claim amount, and applies the project's configured escalation threshold.

The demonstration threshold is:

`ESCALATION_THRESHOLD = 5000`

This threshold is a rule created specifically for this project demonstration and is not presented as an external claims-industry policy.

Because this rule is implemented in application code, its enforcement does not depend solely on the model following prompt instructions.

## System 2: Context Strategy

### Context Reduction

The context-management strategy is implemented in:

`context-strategy/src/context_builder.py`

The system separates information into three categories:

- Critical Case Facts are preserved.
- Relevant events are retained.
- Historical information is summarized.

Context budget measurement is implemented in:

`context-strategy/src/budget.py`

The generated artifact is:

`context-strategy/artifacts/budget.json`

The successful run measured:

- Raw context: 751 estimated tokens
- Assembled context: 169 estimated tokens
- Reduction: 77.5%
- 50% reduction target met: True

The token counts use the deterministic approximation defined in
`estimate_tokens()`, which estimates one token for every four
characters. These numbers therefore represent the project's
reproducible token estimate rather than an exact model tokenizer count.

### Information Preserved and Summarized

Critical information is preserved verbatim in the Case Facts block,
including the case ID, customer, product, severity, status, and current
issue.

Lower-priority historical information is compressed using
`summarize_history()` rather than retaining the complete history in
the assembled context.

Events are filtered by `select_relevant_events()` so that events marked
as irrelevant are excluded from the assembled context.

This strategy reduced the estimated context from 751 tokens to 169
tokens while retaining the information needed by the evaluation.

### Answerability Evaluation

Evaluation logic is implemented in:

`context-strategy/src/evaluation.py`

Six evaluation questions are defined in `EVALUATION_QUESTIONS`.

The full assembled context achieved:

**6/6 correct**

This exceeds the required minimum of 5/6.

The evidence is generated in:

`context-strategy/artifacts/evaluation-full.json`

### Case Facts Control Experiment

A control context is created by:

`assemble_control_context()`

The control removes the Case Facts block while retaining the other
context components.

The control evaluation achieved:

**0/6 correct**

Compared with the full score of 6/6, all six evaluation questions
regressed:

`Q1, Q2, Q3, Q4, Q5, Q6`

This demonstrates that the Case Facts block contains information
necessary for answering the evaluation questions and is not simply
additional context overhead.

The comparison evidence is generated in:

`context-strategy/artifacts/evaluation-comparison.json`

## System 3: Claude Code Harness

### Configuration Hierarchy

The Claude Code harness is configured under:

`claude-harness/`

The main project instructions are defined in:

`claude-harness/CLAUDE.md`

The root instructions import modular standards using:

`@.claude/standards/api.md`

and:

`@.claude/standards/testing.md`

Keeping these standards in separate files allows project guidance to remain modular instead of placing every convention in one large instruction file.

### Path-Scoped Rules

Path-scoped rules are stored in:

`claude-harness/.claude/rules/python.md`

and:

`claude-harness/.claude/rules/tests.md`

The rule files use YAML frontmatter containing glob patterns to determine which files receive the corresponding guidance.

A path-scoped rule is preferable to adding multiple directory-level `CLAUDE.md` files when a convention needs to apply to matching files across different parts of the codebase.

For example, the test rule can target test files through glob patterns without duplicating the same testing guidance in multiple directories.

### Project-Scoped Command

The project verification command is defined in:

`claude-harness/.claude/commands/verify.md`

The command provides a repeatable verification workflow that runs the configuration validator and automated tests.

### Forked Investigation Skill

The investigation skill is configured in:

`claude-harness/.claude/skills/investigation/SKILL.md`

The skill declares:

`context: fork`

The allowed tool set is restricted to:

- `Read`
- `Grep`
- `Glob`

The skill intentionally excludes modifying tools such as `Write`, `Edit`, and `Bash`.

Forked context is appropriate for investigation because exploratory repository evidence and investigation notes can remain isolated from the primary working context.

### Configuration Validation

## System 4: Layer 3 Orchestration

### Tiered State Architecture

The Layer 3 orchestration system is implemented under:

`orchestration/`

The system separates operational information into hot, warm, and cold state.

Cold-state defect history is managed in:

`orchestration/src/defect_store.py`

Warm and hot state are managed in:

`orchestration/src/state.py`

The main orchestration logic is implemented in:

`orchestration/src/orchestrator.py`

This separation keeps the active working state compact while allowing a larger defect history to remain available through SQL-backed cold storage.

### SQL-Filtered Defect Retrieval

**2 defects**

- `DEF-1001`

`orchestration/src/defect_store.py`

The SQL query filters by `shift_id` and active statuses instead of loading the complete defect history as the active shift context.

The resulting evidence is recorded under run:

### Hot-State Budget

The hot state intentionally contains only information required for active orchestration, such as the shift identifier, checkpoint, current status, and active defect identifiers.

This avoids copying the complete cold-state defect history into the active state.

### Crash Recovery

Crash-recovery logic is implemented in:

`orchestration/src/recovery.py`

The configured staleness threshold is:

`STALE_AFTER_SECONDS = 1800`

This corresponds to **30 minutes**.

The successful evidence run demonstrated two recovery paths.

A recent checkpoint resulted in:

`resume`

A stale checkpoint resulted in:

`fresh`

Therefore, an existing checkpoint is resumed while it remains within the configured threshold. Once the checkpoint exceeds the threshold, orchestration starts fresh.

The recovery evidence is generated in:

`orchestration/artifacts/recovery-evidence.json`

## Deterministic Enforcement Versus Prompt-Based Guidance

The projects distinguish between model guidance and deterministic application enforcement.

A deterministic example is implemented in:

`agentic-loop/src/claims.py`

The `route_claim()` function validates required fields, validates the claim amount, and applies:

`ESCALATION_THRESHOLD = 5000`

Because the routing threshold is evaluated by application code, the outcome does not rely solely on the model following a textual instruction.

Prompt-based guidance appears in the Claude Code harness through files such as:

`claude-harness/CLAUDE.md`

and the modular standards under:

`claude-harness/.claude/standards/`

These files provide instructions and conventions that guide model behavior.

The architectural distinction is that prompt guidance influences how the model should behave, while deterministic application logic is used where the project requires an enforceable and testable rule.
